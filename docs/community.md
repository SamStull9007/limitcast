# Follow and help shape Limitcast

## Get release emails

On the [repository](https://github.com/SamStull9007/limitcast), select **Watch → Custom → Releases → Apply**. Enable email delivery for watching notifications in your [GitHub notification settings](https://github.com/settings/notifications).

This uses your existing GitHub account. Limitcast does not collect your email address or create a separate mailing list. Starring bookmarks the project; use Watch to subscribe to updates. You can change or stop notifications at any time.

## Join the conversation

- [Announcements](https://github.com/SamStull9007/limitcast/discussions/categories/announcements): shipped improvements and concise weekly progress notes.
- [Q&A](https://github.com/SamStull9007/limitcast/discussions/categories/q-a): setup and troubleshooting.
- [Ideas](https://github.com/SamStull9007/limitcast/discussions/categories/ideas): explain the problem you want solved and help prioritize it.
- [Show your setup](https://github.com/SamStull9007/limitcast/discussions/categories/show-your-setup): useful setups and voluntary, reviewed findings.

## Try it for a week

We are looking for an initial cohort of 20 people who regularly use Claude Code, Codex, or Grok. Participation is voluntary; there is no signup or required telemetry.

1. Install the current release and run `limitcast onboard` and `limitcast doctor`.
2. Run `limitcast status` and `limitcast trim` locally. Enable hooks or apply changes only if you choose; restart your coding tool and approve hooks when required.
3. After seven days, review `limitcast results` locally. If you want to share totals, use `limitcast results --share`, inspect every line, and remove anything you do not want public.
4. Post a check-in in Show your setup: which tool you use, whether the first result helped, what confused you, and whether you still use Limitcast.

Do not post prompts, credentials, account IDs, private project paths, configuration files, raw transcripts, or customer information. Context reductions are estimates, not proof of financial savings.

## Permission for user stories

A check-in is feedback, not permission to publish a testimonial. If you want your experience considered for a case study, explicitly say whether we may quote your words and whether to use your GitHub handle or remain anonymous. Review the final text and measurements before publication. We will distinguish observations, estimates, and limitations.

## What we measure

Use weekly aggregate snapshots of GitHub watchers, discussion participation, and voluntary returning-tester check-ins. Keep npm downloads separate: downloads are not unique users or evidence of retention. GitHub does not provide us a mailing-list subscriber database. No usage tracking is added to the CLI for this community program.

Learning targets for the first month: 20 voluntary testers, 10 reporting continued use after a week, and 3 permissioned user stories. These are targets, not reported results.

## Weekly updates

Publish one useful Announcements post each week: one verified improvement, one relevant screenshot or example, one useful command, and one question. If nothing shipped, say so and share a useful finding or an open question. Urgent fixes can ship immediately; do not create package releases just to send notifications.

A Friday workflow opens one maintainer draft issue using the [weekly-update template](../.github/weekly-update.md), and leaves an existing open draft alone. The maintainer checks the facts and publishes the announcement; it does not post promotions or send email automatically.
