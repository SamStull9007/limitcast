# Market position and customer evidence

Research date: 27 October 2026. This is a documented-capability comparison, not an exhaustive market search or verified retention.

## Recommendation

Start with heavy Claude Code users who run agents, maintain a substantial MCP/skill setup, and also use Codex or Grok. Sell predictable capacity and understandable controls. Test willingness to pay against strong free alternatives before raising price.

Independent monitoring, optimization and guard products plus native provider investment establish an active problem category. They do not establish how many people will pay Limitcast $9/month.

## Defined differentiation

The candidate bundle is local credential-free readings, burn-rate clock-time forecasts, provider-specific new-agent controls, reversible unused-context cuts with a keep-list, and one explanation of usage/controls/value. Support differs by host: Grok needs a dollar cap; Claude-only functions must be labeled.

No reviewed primary source established this entire bundle with the same behavior across Claude Code, Codex and Grok. This limited finding is not “the only product in the market.” A different bundle solving the same customer's problem remains competition.

| Product | Monitoring / forecasting | Active controls | Optimization and reporting | Implication |
|---|---|---|---|---|
| Limitcast | Claude/Codex quota forecasts; Grok with a cap | New-agent controls in three hosts; Claude model/budget controls | Reversible cuts, keep-list, local reports | Test whether integration reduces recurring effort |
| ccusage | Multi-tool analytics, blocks, status line | New-spawn control not documented in reviewed README | Period/model/cache reporting | Basic reports have strong free substitutes |
| CodexBar | Quotas, resets, pacing/burndown, notifications | New-spawn control not documented in reviewed README | Local spend/history | Visibility alone is insufficient |
| ClaudeBar (tddworks) | Multi-provider quota displays and notifications | New-spawn control not documented in reviewed README | Menu-bar monitoring | Convenience matters |
| agent-usage-guard | Claude plan windows and rapid-burn thresholds | Agent, context and loop protection | Local intervention reports | Claude protection has a capable free alternative |
| CodeBurn | Broad reports, live quota and pacing | Configurable Claude session-dollar caps | Waste analysis, apply/undo, follow-up | Closest broad alternative; compare workflow outcomes |
| Native Claude Code | Usage statistics and attribution | Native spend/settings controls | Context/MCP/model advice and some fixes | Native improvement is current competition |

“Not documented” means unknown in this review, not proof of absence.

## Market requirements to validate

These are hypotheses, not completed interviews:

1. Recurring capacity interruptions or runaway runs cause consequential delayed work, extra usage, attention loss or administration.
2. Installation and the first personal finding take little assistance.
3. Controls are explainable, appropriately timed, reversible and do not damage task quality.
4. Users benefit after the initial trim; a subscription needs a continuing job.
5. Users prefer this workflow to native controls, CodeBurn, a dedicated guard or their current setup.
6. Real customers choose the actual price and later renew.

For teams, also validate deployment, permissions, privacy, administration and procurement. Central collection waits for repeated needs in 3–5 team interviews and two committed pilots.

## Discovery questions

- What tools/plans do you use, and how often do you run parallel agents?
- Describe the last limit or unexpectedly large run that interrupted work. What happened next?
- What do you use now, and what still takes effort or feels unreliable?
- Observe install and a normal task: where do you hesitate, and can you tell whether protection is loaded?
- Which suggested cuts would you keep? Did undo restore the workflow?
- Was each hold useful, unnecessary or overridden? Did model choice affect quality?
- After a week, what would you miss if Limitcast disappeared?
- Offer the actual price. If declined, what would you use instead, and why?

Record negative evidence. Obtain separate permission for public quotes; never collect prompts/source as marketing evidence.

## Learning gates

- First 10: target seven useful activations; record every setup failure and unnecessary intervention. Fix recurring blockers before broad recruitment.
- First 50: target thirty confirmed eligible day-seven active users and five verified payers. Unknown follow-up stays separate.
- Month two: verify renewal when each actual billing period becomes due. Annual customers are not failed monthly renewals.
- Expand when customers explain recurring value and payment/renewal evidence accumulates. Set acquisition spending from observed margin and retention.

These are internal decision targets, not market benchmarks or forecasts. Free use without payment suggests a value/packaging question; paid abandonment suggests continuing-value/trust problems; installation failure requires activation repair.

## Positioning to test

“Get more work from your AI coding plan. Forecast your limits, control agent burn, and trim unused starting context—from one local tool.”

Demonstrate the complete workflow with external evidence. Keep host limitations and estimation labels explicit. Do not promise universal lockout prevention, exact counterfactual/cash savings, or exhaustive uniqueness.
